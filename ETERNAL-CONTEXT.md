## 0. How to use this document

This file exists so that **any AI model — ChatGPT, Claude, Gemini, a local model, a custom agent — can be dropped into this project cold and immediately know what it is, what has been done, why, and what is still open.**

The owner of this project is **not a programmer**. If you are an AI reading this and then talking to them, explain things in plain language. Do not assume they can read a stack trace, evaluate a library choice, or judge whether a diff is safe. When you need a decision from them, describe the *consequence* of each option in ordinary words, not the mechanism.

Everything in this document was verified against the repository on 2026-08-19 unless explicitly marked as a claim, an assumption, or an open question.

**Read sections 1–4 for orientation. Read 5–8 for the full history. Read 9–12 before changing anything.**

## 1. What Eternal is, in one paragraph

Eternal is a desktop AI agent for Linux. It runs on the user's own computer, connects to whatever AI model provider they choose (OpenRouter, OpenAI, Anthropic, a local endpoint), and can use tools, write and improve its own skills, remember things across sessions, run scheduled jobs, and talk to the user through a desktop app, a terminal interface, or chat platforms like Telegram and Slack. It is a **private, rebranded fork** of an open-source project called **Hermes Agent**, built by Nous Research. The owner's goal is to **sell it as a closed-source paid product**, distributed as a downloadable Linux app.

## 4. How the system is put together

Eternal is not one program. It is five layers, and understanding which layer a problem lives in is usually most of solving it.

```
┌─────────────────────────────────────────────────────────────┐
│  DESKTOP APP  (Electron + React)         apps/desktop/       │
│  The window the customer sees. TypeScript. Also holds the    │
│  licence gate, crash reporting, and update checking.         │
├─────────────────────────────────────────────────────────────┤
│  TERMINAL UI  (Ink/React)                ui-tui/             │
│  A full text interface for people who live in a terminal.    │
├─────────────────────────────────────────────────────────────┤
│  WEB DASHBOARD  (React + Vite)           web/  eternal_cli/  │
│  Browser-based control panel, served by the agent itself.    │
├─────────────────────────────────────────────────────────────┤
│  AGENT RUNTIME  (Python 3.11)            agent/  tools/      │
│  The actual brain. Model calls, tool execution, memory,      │
│  skills, cron, subagents, context compression.               │
├─────────────────────────────────────────────────────────────┤
│  PLATFORM PLUGINS  (Python)              plugins/platforms/  │
│  Telegram, Slack, Discord, WhatsApp, Signal, Matrix, and 16  │
│  more. A single gateway process fans out to all of them.     │
└─────────────────────────────────────────────────────────────┘
```

**Key structural fact:** the desktop app **bundles its own Python interpreter**. It does not use whatever Python the customer happens to have. This was a deliberate change made early in the fork (commit `787b32858f`) and it is the reason the product can be installed by a non-technical customer at all. `apps/desktop/scripts/stage-agent-runtime.mjs` downloads a standalone CPython build, verifies it, and packs it into the app.

## 5. History, phase by phase

The fork's own work divides into five phases. Every commit message is written to say *what problem it solved*, not what it touched — reading `git log --oneline` is genuinely informative here.

### Phase 0 — The fork and the rebrand (2026-08-16 → 08-17)

The project began as a straight copy of Hermes Agent with the name changed. A script, `scripts/rebrand-to-eternal.py`, did the bulk substitution.

Mechanical renaming across a 23,000-commit codebase went wrong twice, in the same way both times: it renamed things that were **not** the project's to rename — upstream package names, third-party identifiers, test fixtures that asserted on exact strings. Two follow-up commits (`0e2abfa14d`, `b055e5a211`) walked that back.

**Lesson worth carrying forward:** a rebrand is not find-and-replace. Names that belong to someone else must survive it.

### Phase 1 — Cutting the cord to Nous (2026-08-17 → 08-18)

A fork that still phones home to the original author's servers is not a product you can sell. This phase, twelve commits, systematically severed every runtime dependency on Nous-owned infrastructure:

- `3213af124d` — stopped shipping Nous Research as the app's identity
- `a31a22e9b8` — stopped advertising Nous Research in the `User-Agent` on **every user API call**
- `d1792f3e0d` — **stopped uploading user diagnostics to Nous Research**
- `6cfb486765` — stopped fetching the model catalogue from a host not under our control
- `bb4e289ba4` — stopped fetching plugin and skill indexes from Nous-owned hosts
- `8b9ad103f4` — pointed self-update at our repo, not upstream's
- `f1512f2dfa` — removed the Nous-hosted skill sync default
- `6085c4b1dd`, `ba33d00c4f`, `2df0b6dd75`, `db6250a668`, `0c03801140` — removed the user-facing Nous surface: portal login, provider entries, billing sections, `/topup` and `/subscription` commands, dashboard auth

`a1281d4add` then fixed the 20 genuine test failures this surgery exposed.

**The diagnostics one matters most.** Until commit `d1792f3e0d`, every install silently sent usage telemetry to a third party. Selling software that does that, without disclosure, would have been a serious problem.

### Phase 2 — Standing on our own infrastructure (2026-08-17)

- `787b32858f` — **bundled the agent runtime.** The single most important architectural change in the fork. Before it, installing Eternal meant the customer needed the right Python, on the right version, with the right build flags. After it, the app carries its own.
- `71112f9324` — refuses to build a bundle for a platform that has not been verified, rather than shipping something broken.
- `a1230d5c37` — fixed two bugs that broke *every* install and all 18 CI runs.

### Phase 3 — Making it actually install (2026-08-18)

- `014f508b60` — **the AppImage worked exactly once.** Second launch failed. Fixed.
- `215b02862d` — made the app open on Ubuntu and Debian, and patched two npm security advisories.
- `276de99450` — re-stage the agent source on every build, so builds stop silently shipping stale code.
- `c317234b52` — build the vendored terminal-UI bundle before its tests run.

### Phase 4 — Making it sellable (2026-08-18 → 08-19)

This is the current phase and the bulk of recent work. Detailed in §6.

## 6. What was built to make it a product

Fourteen commits over two days. Each is described here with the problem it solved and how the fix was proven, because **every one of these was verified by running the thing, not by reading the code.** That approach caught several bugs that review alone would have missed.

### 6.1 Update notifications — `9188ffc16b`, `95adb01246`

**Problem.** A packaged app has no way to tell a customer that a new version exists. The inherited self-update mechanism assumed a git checkout — it tried to run git commands and, in a packaged install, reached for the *private* source repo, which a customer cannot access. Recovery attempts produced 404s.

**Solution.** `apps/desktop/electron/release-check.ts`. A **notify-only** design: the app reads a small JSON manifest from the public releases repo, compares versions, and if a newer one exists, tells the user and offers a link. It never downloads or installs anything by itself.

- Manifest: `https://raw.githubusercontent.com/riddhimaaan/eternal-releases/main/latest.json`
- The manifest is size-capped at 64 KB and **any `downloadUrl` that is not `https:` is refused.** This matters: the manifest is fetched from the internet, so it is untrusted input.
- 23 tests.

`95adb01246` additionally made a packaged install stop asking a private repo to repair it. `checkPackagedRelease()` in `main.ts` branches on `IS_PACKAGED` *before* any git work happens.

### 6.2 Electron security advisory — `17578ac218`

Electron 40.10.6 carried a sandboxed-iframe advisory. Upgraded to **41.10.3**, not the latest 43 — 41 was the minimum version that closed the advisory without dragging in a major-version migration that would have needed its own testing round.

### 6.3 The SQLite corruption bug — `9b2be278d2`

**Problem.** The bundled CPython shipped SQLite 3.49.1, which has a bug that **corrupts WAL-mode databases**. Eternal stores the customer's entire conversation history, memory, and session index in SQLite. Shipping this meant shipping data loss.

**Solution.** Moved to a python-build-standalone release carrying SQLite 3.53.1, and added a **build-time guard** — `assertSafeSqlite()` / `verifyStagedInterpreter()` — that refuses to produce a build whose interpreter has a vulnerable SQLite.

**A mistake worth recording.** The guard was first placed inside `stagePython`, which only runs on a fresh download. Routine builds hit the "already staged" cache path and skipped it entirely — the guard existed and never fired. It was moved into `verifyStagedInterpreter`, which covers **every** path: fresh, cached, and `--skip-python`. This was then proven by planting a deliberately vulnerable interpreter in a fake cache directory and confirming the build refused to proceed.

**The general lesson:** a safety check that is never executed is worse than no check, because it creates false confidence. Always prove a guard fires.

### 6.4 Private container registry — `46182bd78e`, `034d43471b`, `7d39441e4e`

**Problem.** The Docker path still pointed at upstream's public Docker Hub registry. For a closed-source product, the image must be private.

**Solution.** Repointed everything to `ghcr.io/riddhimaaan/eternal` (GitHub Container Registry, private), authenticating with the workflow's own `GITHUB_TOKEN`.

Doing this uncovered that **the image had been unbuildable since the rebrand.** A self-test inside the Dockerfile ran an SQLite FTS5 trigram query searching for the literal `'erm'` — a fragment of "h**erm**es". After the rename there was no "hermes" in the data, so the query returned nothing and the build failed its own health check. Two commits, because the same broken query existed in `tests/docker/test_sqlite_runtime.py` and the first scan missed it — a 12-minute wasted build. The fix in both places was `'erm'` → `'ern'` (a fragment of "et**ern**al").

Both architectures now build and publish. The published image was **pulled back down and verified as a customer would experience it**.

### 6.5 GitHub Actions cost — `c13c04f8c6`

**Problem.** GitHub gives private repositories 2,000 free Actions minutes a month. Something was consuming the allowance and publishing had started failing with a billing error.

**Investigation.** An initial diagnosis — that a failed card was more likely than exhausted minutes — was **wrong**, based on counting only the Docker workflow's ~40 minutes. Actual measurement showed **CI alone had consumed 1,759 minutes**, roughly 90% of the allowance.

**Cause.** The CI orchestrator ran on every push to `main`. On push, its change-detector fails open, so *every* lane runs: about 50 jobs, ~107 billable minutes, per push. This is correct behaviour for a large open-source project with many contributors. On a one-person private repo it bought nothing — the same suite runs locally in under a minute.

**Solution.**
- `ci.yml` now triggers on `pull_request` and `workflow_dispatch` only. Pull requests still get the full suite; the Actions tab still gives an on-demand run.
- `js-autofix.yml` → manual only.
- Scheduled timers removed from `install-e2e.yml`, `skills-index.yml`, `skills-index-freshness.yml` — inherited from upstream, firing on a schedule, failing, and billing for it.
- The weekly `osv-scanner.yml` security scan was **kept**. It is cheap and it is the thing that catches vulnerable dependencies.

**Result:** ~1,943 minutes/month → ~170.

**Also configured (by the owner):** spending limits of $3.00 each on Actions, Packages, and Codespaces, with "stop usage when limit reached" enabled. Note that container registry storage and bandwidth are currently free on GitHub, so the 2.73 GB image is not itself a cost.

### 6.6 The glibc wall — `3e8fbe83f3`

**Problem.** This is subtle and it was the difference between a product and a personal toy. The AppImage was built on Arch Linux, which ships a very new glibc (2.42). A binary compiled against glibc 2.42 **will not start** on a system with an older glibc — and essentially every stable distribution ships an older one. Ubuntu LTS, Debian stable, RHEL, all of them. The AppImage ran on the owner's machine and nowhere else.

**Solution.** Two parts.

1. `apps/desktop/scripts/portable-glibc.mjs` — a check with `GLIBC_CEILING = [2, 31]`. It scans every shipped binary's ELF string table for `GLIBC_x.y` version literals and fails the build if anything requires newer than 2.31.
2. `apps/desktop/scripts/build-node-pty-portable.mjs` — the native terminal component (`pty.node`) must be *compiled* against an old glibc, not just checked. It is built inside a `node:20-bullseye-slim` container (Debian 11, glibc 2.31) against the pinned Electron ABI, via podman or docker. npm script: `build:pty-portable`.

**Result:** the AppImage now starts on Debian 10+, Ubuntu 18.10+, and RHEL 8+.

**The principle:** build old, run everywhere. Backward compatibility in glibc is one-directional.

### 6.7 Slack plugin and dead timers — `cb66e1010a`

Two unrelated small problems. The Slack adapter guarded `import aiohttp` in the *same* try/except as `slack_bolt`, so a missing `slack_bolt` silently disabled aiohttp too, and the plugin failed to load at boot. Split into separate guards.

**Note for future work:** an audit found roughly **40 bundled plugins that import packages the bundle does not ship** — discord, telegram, matrix, teams, playwright, several memory providers. They fail silently. Slack was only audible because it loads at startup. **This is a deliberate open product decision, not a bug to fix blindly** — see §10.

### 6.8 The false "config is 2 years old" warning — `41bdfa75d3`

Every container user, on first run, was greeted with a warning that their configuration predated version 12 and might be broken. It was false. `cli-config.yaml.example` had no `_config_version` field, so the version check read it as ancient. Added `_config_version: 37`, plus a test (`tests/eternal_cli/test_example_config_version.py`) that pins the example to the code's actual `DEFAULT_CONFIG` value so it cannot drift again.

Small bug, disproportionate damage: it was the **first thing a paying customer would ever see.**

### 6.9 Crash reporting — `5e7166c5c4`, `4a535abe91`, `c603a4d0cc`

**Requirement from the owner:** open source, self-controllable, no third-party plugin lock-in. Chosen: **GlitchTip** — an open-source, self-hostable backend that speaks the Sentry protocol, so the standard Sentry SDK works against it and the backend can be moved in-house later without touching the app.

**Design, in `apps/desktop/electron/crash-reporting.ts`:**

- **Opt-in, not opt-out.** `decideCrashReporting()` treats `not-asked` as a state distinct from `no-consent`, so the app can tell "never asked" from "asked and declined".
- Development builds never report.
- `ETERNAL_DISABLE_CRASH_REPORTS` kills it entirely.
- `scrubEvent()` runs recursively and cycle-safely over the whole event: drops entire `env` blocks, and strips OpenRouter, Anthropic, OpenAI, GitHub, Slack, and Google key patterns, JWTs, email addresses, and the user's home directory path.
- 18 tests.

**Status: proven working.** A real crash report was delivered to GlitchTip end to end.

**DSN:** `https://411f328babea4190b2dc538beabf0013@app.glitchtip.com/27017` (overridable via `ETERNAL_CRASH_DSN`).

**Not yet reachable by a customer** — there is no consent prompt UI, so in practice it never fires in a shipped build. See §10.

### 6.10 The licence gate — `783a771b61`, `d7d5c91298`, `3950ccae28`, `2a8be62272`

This is the mechanism that makes Eternal sellable rather than merely downloadable.

**How it works.**

A licence key is a small signed token. Signing uses **Ed25519** via Node's built-in `node:crypto` — no third-party dependency. The private key signs; the public key, which is safe to embed in the shipped app, can only verify. **A key cannot be forged without the private half.**

Verification happens **on the customer's own machine and works offline.** The app does not need to reach a server to know a key is genuine.

**But a signature cannot be withdrawn.** It stays valid forever. A refund, a chargeback, or a key posted on a forum would be unenforceable. That is the *only* reason a server exists.

**The server** (`services/license/worker.js`, a Cloudflare Worker) answers exactly one question: *is this key still good?* It:
- verifies the signature **before** looking anything up, so it cannot be used as an oracle
- returns HTTP 503 — not "invalid" — if it is misconfigured, so an operator error never revokes everyone's software
- **stores nothing about callers.** No keys, no identifiers, no addresses, no history. Eternal is sold on the promise that the customer's work stays on their machine; a licence check that quietly logged when each customer opened the app would undercut that.

**Failure policy — deliberately generous.**
- Confirmation is attempted every **7 days** (`CONFIRM_EVERY_DAYS`).
- If the service is unreachable, the app keeps working for **30 days** (`OFFLINE_GRACE_DAYS`).
- **If the service is down, nobody's paid software stops working.** Revocations simply take effect later.

**States:** `not-enforced`, `unlicensed`, `invalid`, `expired`, `revoked`, `active`, `active-unconfirmed`, `stale`.

**Deployed:** `https://eternal-license.riddhimanbania381.workers.dev`
**KV namespace id:** `9d6cbb7638a04a5db853ef47b658d171`

**Verified end to end on 2026-08-19:** a genuine key returned `valid`; a key signed with a different keypair returned `invalid`; malformed input returned `invalid`; a revoked key returned `revoked`; another customer's key was unaffected.

**Two bugs caught during that verification:**

1. **A fresh key reported `stale`.** Silence was being measured from zero rather than from first use, so a brand-new licence looked like one that had gone unconfirmed for a month. A customer would have paid and then immediately been told their key could not be confirmed. Fixed: never-confirmed is now its own case, returning `active-unconfirmed` with no alarming message.
2. **`license-config.ts` did not exist.** The keygen tool and README both instructed the owner to edit a file that had never been created. Fixed in `3950ccae28`, which also made an **unconfigured gate default to open** (`not-enforced`) — so merely landing this code could never lock anyone out, including the owner.

**Also note:** Cloudflare KV caches the *absence* of a key for up to a minute. For a short while after revoking, the service can still answer `valid`. This is normal and documented. During testing the same key returned `valid` immediately after revocation and `revoked` fifteen seconds later.

## 9. Runbook

### Build the desktop app for Linux

```bash
cd /home/nothingness/work/eternal/apps/desktop
npm run build:pty-portable   # only when the native terminal component changed
npm run dist:linux           # produces AppImage, .deb, .rpm
```

`dist:linux` runs `prebuilder`, which stages and verifies the bundled Python (SQLite guard) and then electron-builder. The glibc ceiling check runs during packaging and **will fail the build** if anything requires newer than glibc 2.31.

### Run tests

```bash
cd /home/nothingness/work/eternal/apps/desktop && npm test          # vitest, all desktop projects
cd /home/nothingness/work/eternal && python -m pytest tests/        # python suite
```

### Issue a licence to a customer

```bash
node services/license/issue.mjs cust_0001
```

Use an opaque identifier you can look up in your own records. The tool **refuses email addresses**, because keys end up in support threads and screenshots.

For a time-limited subscription rather than a perpetual licence:

```bash
node services/license/issue.mjs cust_0002 --days 365
```

### Withdraw a licence

```bash
npx wrangler kv key put --binding=REVOKED "cust_0001" "refunded 2026-08-20"
```

Takes effect the next time that install checks in — within a week. **Allow at least a minute before concluding it did not work** (KV negative caching). The stored note is for the seller's records and is never sent to the customer.

### Publish a new version

1. Build and test locally.
2. Upload the artefacts to a GitHub release on `riddhimaaan/eternal-releases`.
3. Update `latest.json` in that repo — `version`, `downloadUrl` (must be `https:`), and `notes`.
4. Existing installs notice within their next check and offer the link. Nothing auto-installs.

## 11. Business model and monetisation

**Goal:** sell Eternal as a paid, closed-source Linux desktop application.

**What exists:** a licensing mechanism that can issue, verify, and withdraw keys, deployed and verified.

**What does not exist:** any way to take money.

### The issuance trade-off (unresolved, deferred by the owner)

Right now, issuing a licence means running one command by hand. That does not scale past a handful of customers. There are two ways forward, and they trade off differently:

| Approach | How it works | Cost |
| --- | --- | --- |
| **Automated issuance** | A webhook signs a key the moment payment clears | The **private signing key must live in the cloud**. If that host is breached, anyone can mint licences. |
| **Pre-minted inventory** *(recommended)* | Mint a batch of keys offline; a webhook hands out the next unused one | The signing key **never leaves the owner's machine**. Requires topping up the batch periodically. |

### Payment provider

International sales originating from India make a **merchant of record** the sensible choice — the provider handles VAT/GST registration and remittance across jurisdictions rather than leaving it to the seller. Candidates: **Gumroad**, **Lemon Squeezy**, **Paddle**.

**Recommendation on file:** defer all of this until there are actual customers. Manual issuance is entirely adequate for the first several sales, and the first sales will teach more about pricing and packaging than any amount of upfront automation.

## 12. Rules of engagement for AI assistants

Working conventions established on this project. Following them will make your work fit; ignoring them has caused real problems here before.

### Verify by running, not by reading

**Every claim in this document that says "verified" means something was actually executed.** This convention has repeatedly caught bugs that code review missed: the SQLite guard that never fired, the image that had been unbuildable for days, the licence gate that would have greeted paying customers with an error, the AppImage that only ran on one machine. Do not report something as working because the code looks correct.

### Scan completely before declaring a fix complete

The FTS5 trigram bug was fixed in the Dockerfile, then found again in the test file, costing a 12-minute rebuild. When a wrong pattern exists, search the **whole repository** for it before saying it is fixed.

### Security constraints — these are absolute

- **Never read, print, transmit, or commit** `~/.eternal-license-signing-key.pem`.
- **Never enter API keys or credentials into any application field**, regardless of who supplies them or how they are framed.
- **Never perform OAuth authorisation** on the owner's behalf (`wrangler login`, `gh auth refresh`, and similar). Provide the command; the owner runs it.
- **Never set spending limits or make financial changes.** Describe what to set; the owner sets it.
- **Never capture full-screen screenshots.** The owner's screen is private.

### Commit message style

Messages say **what problem was solved**, in plain language, not what files moved. Compare "Stop greeting every container user with a false 'config is 2 years old'" against "fix: update cli-config.yaml.example". The first tells a reader why the commit exists. Match this style.

### Talking to the owner

They are **not a programmer**. Explain in plain language. When presenting a choice, describe consequences rather than mechanisms. Do not present a menu of options without a recommendation. They have explicitly asked to be **reminded about the outstanding UI work**, so surface it.

### Do not commit or push unless asked

The owner approves each commit and push explicitly. Prepare the work; ask before landing it.

## 13. Plain-language glossary

For the owner, and for any AI that needs to explain these terms.

| Term | What it means here |
| --- | --- |
| **Fork** | A copy of someone else's open-source code that you then develop independently. |
| **MIT licence** | A permissive licence. You may sell software built on MIT code, provided you keep the original copyright notice. Eternal does. |
| **AppImage** | A single downloadable file that runs a Linux app without installation. Like a portable `.exe`. |
| **glibc** | A core Linux system library. Software built against a new version will not start on a computer with an older one — which is why Eternal is now built deliberately against an old one. |
| **Electron** | The technology behind the desktop window. Chrome and Node.js in a box. |
| **Container / Docker image** | A packaged copy of the whole app plus everything it needs, so it runs identically anywhere. |
| **ghcr.io** | GitHub's private storage for container images. |
| **CI / GitHub Actions** | Automated testing that runs on GitHub's computers. Billed by the minute — hence the cost work. |
| **SQLite / WAL** | The small database inside the app holding conversations and memory. WAL is a mode it runs in. A buggy version could corrupt it, which meant losing customer data. |
| **Ed25519** | The maths behind licence keys. A private key creates them; a public key can only check them. |
| **Cloudflare Worker** | A tiny program running on Cloudflare's servers. No server to rent or maintain. Free at this scale. |
| **KV** | A simple key/value list. Here, the list of withdrawn licences. |
| **GlitchTip** | Open-source crash reporting. When the app breaks on a customer's machine, it can send an anonymised report. |
| **DSN** | The address crash reports are sent to. |
| **Merchant of record** | A payment company that legally sells on your behalf and handles international tax for you. |
